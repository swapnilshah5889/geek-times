# Frontend reader map (pre-cutover audit)

Status: read-only audit. No source changed. Branch `v1`, HEAD `b49b8ad` (Supabase loader cutover; browser reads `v_live_story` / `v_live_library_entry`).
Scope: every runtime data read in `src/` and `scripts/`. Line numbers refer to the files as they stand at HEAD.

Two facts frame everything below:

- Only two kinds of data come from Supabase: the story document (`PaperDoc`) and the live library story entries (`LibraryStory`). Everything else the UI renders comes from `public/data/*.json`.
- The archive (`Archive` = site + vocab + index + library) is loaded whole, before render, and every page takes it as a synchronous prop.

## Section 6: Sync vs async notes and risks

### 6a. Async today

- `loadArchive`, `loadLibrary`, `loadEdition`, `loadSite`, `loadVocabulary`, `loadSearchIndex`, `getJson`, and both `StoryDataSource` methods are `Promise`-returning.
- Every async load runs inside `load(route)` in `App.tsx:60`, called inside `Promise.resolve().then(...)` at three sites (`App.tsx:128`, `:155`, `:168`). Every page render sees a fully loaded `Archive`.
- `loadSite` is also called on its own at `App.tsx:193`, outside `load()`, for the masthead.

### 6b. Sync callers that will break if these become async

The rewrite will make the loaders async. These synchronous consumers must stay fed with already-loaded data, or they need to move into the async path:

1. **`mediaBaseFor(site)` at render time.** `HomePage.tsx:337` (`useMemo`), `SitePage.tsx:16` (`useMemo`), `FeedPage.tsx:50` (inline JSX). Also used in `editionFromInitial` (`initial-snapshot.ts:61`). It needs `site` to be present; once `site` comes from the store, these are fine as long as `site` is not loaded lazily.

### 6c. Behavior risks for the rewrite

1. **Supabase only covers story docs and story entries.** `site`, `tags` vocabulary, `search-index`, and every field of `library` other than `stories` (`front`, `issues`, `companies`, `nodes`, `relations`, `fields`, `volumes`, `storylines`) still come from `public/data`. Removing file mode means building read paths for all of them, or the home page, search, feed, map, and issues break. This is the biggest scope gap.
2. **`search-index.json` is derived from file story data.** `build-index.ts` (run by `predev` and `prebuild`) computes covers, moments, tags, and feed entries from `papers/*.json`. In Supabase mode the search, feed, snacks, numbers, and paper covers reflect the file, not the live Supabase story. An edit published to Supabase does not update them until the index is rebuilt. Stale-data risk.
3. **`loadEdition` gates on `site.json`.** A story must appear in `site.papers` to open, even in Supabase mode. The Supabase read is keyed by slug but the check is against the file.
4. **Publishing reads the files.** `scripts/publish-to-supabase.ts` (`:708-711`) and `seed-editorial-from-library.ts` (`:41-42`) read `public/data/library.json`, `tags.json`, and `papers/<slug>.json` as the authoring source. Deleting `public/data` breaks the importer. Authoring has to move first, or the import must be redefined.
5. **Prerender bakes data into HTML.** `prerender-routes.ts` reads `site.json` and `library.json` at import. The snapshot embeds the whole `archive` and `edition.doc` into each prerendered HTML file. Prerender needs a non-file source for routes, and the snapshot schema needs revisiting, or the `source` check in `check-prerender.ts:77` and `initial-snapshot.ts:79` must be relaxed.
6. **Sample pages skip Supabase.** `App.tsx:64` and `:75` return the `sample` view before `loadEdition` runs, so `/papers/<sample>` never reads Supabase. A real story whose library shell says `real: true` but whose DB row is missing throws "has no live version". Matches the note in `docs/handoffs/supabase-loader-cutover.md:69`.
7. **Caches are page-lifetime, not navigation-lifetime.** `getJson` caches every URL, and `pickSource` memoizes the Supabase client and its per-slug and library promises. A reload is needed to see a change made after first load. The post-hydration refresh (`App.tsx:153-165`) re-runs `load()` and replaces the view only when `JSON.stringify` differs. It never re-reads after that, and a failure shows only the "may be out of date" banner.
8. **Double fetch of site and vocab.** `loadEdition` calls `loadSite` and `loadVocabulary` again, which work only because `getJson` caches them. Any rewrite that drops the cache will double the network calls.
9. **Invalid `VITE_DATA_SOURCE` throws at import time.** `readInitialData` (`initial-snapshot.ts:79`) calls `sourceMode()` without a guard, so a bad value throws from `main.tsx` before React mounts.
10. **Stale documentation.** `docs/handoffs/supabase-loader-cutover.md` describes the pre-cutover `published_version` queries and gives line numbers for them. The code already uses `v_live_story` and `v_live_library_entry`, and its line references do not match. Its risk note 5 says `docs/decisions.md` entry 48 still describes `published_version`. Entry 48 (`docs/decisions.md:411-417`) describes the file/supabase switch. Both need a docs update, which needs lead sign-off.
11. **`.env` defaults the local dev server to Supabase.** `.env:10` sets `VITE_DATA_SOURCE=supabase`. Because `.env` is gitignored, a fresh clone defaults to file mode. Anyone running a clean clone gets a different data path than this checkout.
12. **Name collision.** `HomePage.tsx:32` defines a local `useEdition(archive)`, separate from the exported `src/edition.ts` `useEdition()`. Not a bug, but it is easy to get wrong during the rewrite.

### 6e. Summary

- Frontend data reads: 9 public JSON reads (`site`, `tags`, `library`, `search-index`, `papers/<slug>`) and 2 Supabase views. Every read ends in the same `Archive` or `Edition` shape.
- Async surface: 8 loaders plus 2 source methods, all consumed in `App.tsx:load()` or `load.ts`.
- Sync surface: all page helpers and render-time readers listed in Section 6b.
- Scripts that read `public/data`: `build-index`, `prerender-routes`, `publish-to-supabase`, `seed-editorial-from-library`. The last two are the authoring-to-Supabase path.
