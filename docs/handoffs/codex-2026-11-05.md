## The project in a paragraph

**The Geeky Times** is a newspaper-style web app that explains research papers and company engineering
posts to anyone — kids included — with hand-drawn animated SVG illustrations and comic strips. React 19
+ TypeScript + Vite. The UI only renders data (JSON today, Supabase later). Two real stories live:
*Attention Is All You Need* (peer-reviewed) and *Why a bigger deer breaks* (arXiv 2408.04070,
preprint, now the front-page lead). Everything else is `sample: true` placeholder content kept for
layout review.

Design direction: cream newsprint `#f6f0df`, serif masthead, Courier labels, halftone dots, muted
cartoon fills. Three strict labels on every claim (decision 18): *Illustration · numbers invented*,
*From the paper · model design*, *Measured result · peer-reviewed | preprint | company-reported*.

## What has landed since your last review

### New decisions (38–41)

- **38 · Final: no foreign key constraints.** Tables relate through `<thing>_id` columns without
  `REFERENCES`. The replacement controls (transactional publish, unique / check / not-null,
  pre-publish orphan check, orphan monitoring, remap tests) become required, not optional.
  Nested reads (a story with its tags) use SQL views, database functions or server code — not
  Supabase's auto-generated REST embedding.
- **39 · Defer tests, CI and axe to the pre-launch gate.** Investing in Vitest/Playwright/axe/CI
  while the app is pre-v1 (demo tiles, JSON data layer being rewritten against Supabase) slows
  iteration and would be rewritten anyway. A new Phase 4.5 "Pre-launch hardening" section runs them
  as one gate right before Phase 5. Daily checks remain `npm run data`, `npm run build`,
  `npm run lint` and a look at 1280/375.
- **40 · One long-lived `v1` branch, no PR per change.** All day-to-day work commits to `v1` and is
  pushed there. No per-topic feature branches. `main` is never committed to. Owner merges `v1` →
  `main` when they want to release.
- **41 · Rendering: SSG by prerender postbuild; Next.js migration planned later.** A spike script
  (`scripts/prerender.ts`) boots `vite preview`, visits a route in headless Chromium (puppeteer) and
  writes `dist/<route>/index.html`. Vercel serves the prerendered files; the SPA hydrates on top.
  Long term: migrate to Next.js once the spike validates traffic.

## Where we want your review

### Hard questions

1. **SSG prerender spike — is this path durable?** The spike works for SEO but has two acknowledged
   gaps: (a) real users see a flash because `main.tsx` uses `createRoot` not `hydrateRoot` and
   `App.tsx` shows a loading state while it fetches `site.json`; (b) `og:image` points to an SVG that
   Twitter/Facebook/LinkedIn won't render. Is proper hydration (embed data as
   `<script>window.__ARCHIVE__=…</script>`, use `hydrateRoot`) worth the work pre-v1, or should we
   jump straight to Next.js now and skip the puppeteer step entirely? Decision 41 bets on the spike
   plus a later migration; we're open to collapsing those into one move.
2. **Defer-tests call (decision 39).** Is deferring Vitest/Playwright/axe to Phase 4.5 reasonable
   while the data layer is being rewritten against Supabase, or is there a thin slice of tests —
   maybe just the data validator in `scripts/build-index.ts` and the search helpers — worth building
   now?
3. **Single-`v1`-branch call (decision 40).** Pros: no PR overhead, fast iteration. Cons: no review
   gate, parallel sub-agents can't push cleanly to the same branch. Is this the right trade pre-v1?
4. **No-foreign-keys call (decision 38).** You argued the opposite case last round. Decision 38
   confirms no FKs, but makes the replacement integrity controls required. Does the production plan's
   Phase 3 cover them adequately (transactional publish, pre-publish orphan check, remap tests)?
   Anything missing?
5. **Vercel + puppeteer.** Puppeteer downloads ~170 MB of Chromium at install time, which slows
   Vercel builds. The spike's current choice is to run prerender locally (not on Vercel) with
   `PUPPETEER_SKIP_DOWNLOAD=1` on Vercel. Is prerender-locally-and-commit-dist a maintainable
   long-term pattern, or should we move it into a GitHub Action, or does the Next.js migration end
   this question?

### Soft questions

- The Phase 1 slim: only "rendering decision + spike" and "preview deploy" remain. Everything else
  (tests, CI, axe) moved to Phase 4.5. Is there a Phase 1 item we're underweighting?
- `docs/STATE.md` was added to shrink what new agents reload per session (part of a cost-reduction
  pass). Does it scale as the project grows, or should it be sectioned differently?
- Skill routing: each `skills/*/SKILL.md` now carries a `Default model` line (small / medium /
  large). Reasonable fit per skill?
