## Claims Codex should check hardest

1. **Hash strategy for idempotency has a cost trade-off.** Supabase JS exposes size + MD5-style etag on list, not SHA-256. Agent A's choice: on size match, download the remote object and SHA-256 it. For 174 × 1.4 MB this is fine; for any future large-asset migration it will dominate run time. If Codex wants a cheaper check (e.g., trust the MD5 etag, or write a sidecar `<key>.sha256` object alongside each upload), say so and we'll refactor. Current call: correctness over speed.
2. **CORS as a hard blocker in verify mode.** Missing `Access-Control-Allow-Origin: *` exits 1. Supabase Storage *should* send this by default on public buckets, but Agent B could not confirm it from official docs; the owner must test empirically on first run. If a legitimate case exists where ACAO is missing but media still loads (e.g., non-fetch `<img>` use), the gate is too strict — but `MediaView` uses `fetch` for inline SVG animation, so CORS failure is real and this is the right default.
3. **Placeholder heuristic is unit-tested only.** `<500 bytes` or `<rect>`-only is a crude but useful filter. Risk: a legitimate tiny icon under 500 bytes gets excluded. Current live SVGs are 84+ for the three new papers and all are the real art from `86f75aa`, so no false positives expected on the first run — but confirm during Codex's review.
4. **Convert pipeline staging layout has a doubled slug.** `data/intake/<slug>/media/<slug>/<name>.svg`. Chosen so the staged key equals the story `src` (`<slug>/<name>.svg`) — makes Agent A's upload trivial (strip the first two path segments). Alternative is `data/intake/<slug>/media/<name>.svg` with a different mapping. Either works; current one is simpler at the upload boundary.
5. **`convert.ts` publish-time upload hook is not implemented yet.** Only the design-note comment at the top. Until Agent A's upload runs from `data/intake/...` on publish, a newly converted preview story will show broken art in local dev (`publish-to-supabase.ts` does not check media existence). Guard: don't convert a new story until the upload hook lands, or expect to run `npm run media:upload` manually against the staging path.
6. **Restore drill has not run against a real disposable project.** All guards tested offline (missing flags, same-ref refusal, non-empty target, unknown args, export-inside-repo). First real run is still owner-action.
7. **STATE.md line 28 correction is a claim, not evidence.** Fixed from "placeholder grey plates" to "real hand-drawn art in place for every live story (84 SVGs for `resnet`/`google-search`/`dynamo` landed in commit `86f75aa`)". Verified by reading the SVG header of one file per paper (titles "A photo of a cat with a question mark…", "Four kids standing apart…", "A cart name tag goes into a machine…"), not by browser rendering. Codex should spot-check in the actual app if it has any doubt.
8. **Agent E (local-media deletion) was deliberately skipped.** Codex's expanded brief in the repo adds Agent E to remove `public/media/` from Git after A+B evidence lands. Current commits don't do that. If Codex wants it this round, say so; otherwise it's the next-commit task after owner finishes the Storage upload-and-verify loop.
9. **Agent C's `MapPage.tsx`, `FamilyTree.tsx`, `SamplePage.tsx` cleanup in the expanded brief was NOT done.** The accessibility-only Agent C from the ORIGINAL brief was executed; the expanded content-cleanup scope (newsletter, "Out next Friday", `[Company name]`, demo nodes) is still open.
